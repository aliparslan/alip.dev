On building things that last

Why endurance matters more than velocity, and how to build software you won't be embarrassed by in two years.

There's a persistent myth in software that speed is everything. Ship fast. Move fast and break things. Get to market before anyone else. And to some extent, that's true — momentum matters, and perfect is the enemy of shipped.

But speed without intention is just thrashing. I've seen teams ship features in a week that take six months to untangle. I've written code at 2am that I couldn't understand by the following Tuesday. Velocity without durability is a debt you pay with interest.

The compounding cost of "good enough"

When you build something quickly, you make a series of small compromises. Each one seems reasonable in isolation. You skip the test. You hardcode the value. You copy-paste instead of abstracting. You name the variable temp because you'll fix it later.

You won't fix it later.

These compromises compound. Not linearly — exponentially. Each shortcut makes the next shortcut more likely, and each one makes the system harder to reason about. After enough of them, you have a codebase that works but that nobody wants to touch.

The best code is code that's easy to delete, not easy to write.

I think about this a lot. The things I've built that lasted — the ones I'm still proud of years later — aren't the ones where I was clever. They're the ones where I was clear.

What "lasting" actually means

I don't mean lasting forever. Nothing in software lasts forever, and that's fine. By "lasting" I mean:

  • Readable — someone new can understand it without a tour guide
  • Changeable — you can modify behavior without rewriting everything
  • Deletable — you can remove parts cleanly when they're no longer needed
  • Trustworthy — it does what it says it does, and you can verify that

None of these require fancy architecture or complex abstractions. In fact, the fancier the architecture, the less likely it is to last. The best systems I've worked with are almost boringly simple.

An example from a recent project

I was building a data pipeline that needed to process events from multiple sources. The "smart" approach would have been to build a generic event processor with plugins and adapters and a configuration DSL. The kind of thing that looks impressive in a design doc.

Instead, I wrote three separate scripts. One per source. Each one was about 80 lines of code. They shared a small utility library for the output format, but otherwise they were completely independent.

// Each processor is dead simple
async function processStripeEvents(since) {
  const events = await stripe.events.list({ created: { gte: since } });

  for (const event of events.data) {
    const normalized = normalize(event);
    await store(normalized);
  }

  return events.data.length;
}

Six months later, we needed to add a fourth source. It took an afternoon. We needed to remove one of the original sources. It took ten minutes. Nobody had to understand the whole system to change one part of it.

The discipline of simplicity

Simple is hard. It's much easier to add complexity than to resist it. Every abstraction, every layer of indirection, every "just in case" feature — they all feel productive in the moment. But they're usually solving a problem you don't have yet.

Here's what I try to do instead:

  1. Write the obvious thing first. The naive implementation is usually better than you think.
  2. Wait for the pattern to emerge. Don't abstract until you've done the same thing three times.
  3. Name things carefully. Good names are a form of documentation that never goes stale.
  4. Delete aggressively. Dead code is a lie that confuses future readers.
  5. Test the contract, not the implementation. Tests that break when you refactor are tests that prevent refactoring.

I'm not saying don't ship fast. I'm saying invest your speed wisely. The best engineers I know are fast precisely because they've internalized these habits. They don't agonize over architecture — they write the simple thing, ship it, and iterate.

The things that last aren't the clever things. They're the clear things. Build those.
